## rx form

Yes to all four. Here's how I'd approach each, based on the PDF and the current code (pages/api/rxform.ts sends a Mailgun template today).

1. Email that looks like the intake form: React Email + Resend. This is a good fit. I'd build one RxEmail component that copies the PDF's layout: the lab header with the doctor, address, phone, patient and delivery date block, the purple "Appliances Prescription" bar, then two columns. The left column holds the doctor's drawing plus the clasp, screw, spring and color fields. The right column is the full appliance checklist with the chosen ones ticked. Special instructions go along the bottom. Emails need table-based layout, and React Email's Section/Row/Column handle that for you. Setup is verifying the domain in Resend (a few DNS records) and swapping out the Mailgun call. While we're in there I'd fix a current bug: the route returns success even when the email fails to send.

2. Scan upload: yes. As the scan-uploads thread suggested, the browser should upload straight to storage using a signed URL, because Vercel rejects request bodies over about 4.5 MB. The email then carries a download link that expires, not an attachment. The site already uses Supabase, so a private Supabase Storage bucket is the easy choice.

3. Drawing on the arch image: react-sketch-canvas. It puts a drawing layer over mouth.png and comes with pen, eraser, undo/redo and clear. It works with a mouse, a finger or an iPad pencil. I'd add two or three pen colors and a couple of line widths. Heavier tools like Fabric.js or tldraw only make sense if he later wants text or symbol stamps (the paper form says "use symbols"). When the doctor submits, the drawing is flattened onto the arch image as one PNG. That PNG gets saved to the bucket for the lab's records and is also attached to the email as an inline image, so it shows in the left column. That approach avoids two problems: many email clients block data-URI images, and a signed link would stop showing after it expires. I haven't tested inline-image support in Resend yet, so treat that part as inferred.

One caution: scans, drawings and patient names are health information. I'd keep the bucket private and use short-lived links. It's also worth checking whether Resend and Supabase will sign a BAA (a HIPAA business associate agreement) if the lab needs one.


## Scan retrieval

I'm weighing an in-house upload flow against Dropbox for large STL and PLY scans.

My recommendation is to add a scan upload to the RX form doctors already fill out, rather than building a separate login-and-upload portal first. The files go straight from the doctor's browser to cloud storage, and the owner gets an email with the order details and a download link instead of an attachment.

Why this approach

It solves the real problem, which is files too big for email, and doctors don't have to create yet another account. Most labs lose submissions when there's a login in the way.
Each scan stays attached to its RX order, so the owner never has to match up an email with a Dropbox file.
Your Clerk + Convex idea still works later. Accounts can come in v2.1 for order history and re-orders, and they don't need to block uploads.

How it would work

The browser uploads the file directly to storage using a short-lived signed URL. It can't go through a Next.js API route because Vercel caps request bodies at about 4.5 MB, and intraoral scans often run 20 to 200 MB.
Storage: I'd use AWS S3. It handles large resumable uploads well and AWS signs a HIPAA BAA easily. Convex file storage also works with its upload URLs and stays in the stack you like, so choose it if you go all in on Convex. I'd confirm Convex's per-file limits and whether it offers a BAA on your plan before relying on it (I haven't verified those). UploadThing is the easiest option to drop in, but it's the weakest fit for patient data.
Notification: keep the Mailgun email the RX form already sends, and add a link that expires, pointing to the scan in a small private admin page.

Patient data
The scans and RX details are health information. Whatever you pick needs a signed BAA, private storage, links that expire, and no scans sent as email attachments. The current site also has a hardcoded Supabase key, which should be removed either way.

If you want zero build, a Dropbox Business File Request link is a perfectly good stopgap. It's covered by a BAA if he's on a Business plan and signs it, but it won't tie files to orders.
